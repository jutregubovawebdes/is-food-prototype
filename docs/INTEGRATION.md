# Передача в разработку

## Границы поставки

Это согласованный визуальный прототип, а не готовый сервис оформления заказов. Его можно открыть в Cursor как обычную папку и переносить в используемый стек. Внешний вид и основные пользовательские сценарии следует сохранить. Методы API ниже — логические операции, а не существующие endpoints.

При упаковке CSS и меню вынесены из исходного скрипта в отдельные файлы. Для стабильного превью добавлены управляемые часы. Также устранено устаревшее упоминание обновления баланса после 15:00 в tooltip и добавлена проверка дедлайна для создания заказа (в исходном прототипе проверялись только изменение и отмена).

## Согласованные правила

1. Пользователь выбирает несколько комплексов и количество каждого. Переключение вкладок не сбрасывает выбор. Один заказ содержит несколько позиций.
2. Дата в меню и заголовке «Мои заказы на …» — дата питания, не дата оформления. Заказ во вторник на среду, в пятницу — на понедельник. Прототип пропускает субботу и воскресенье; праздничный календарь не согласован.
3. Создание, изменение и отмена доступны строго до 15:00 дня оформления, часовой пояс Asia/Yekaterinburg. Для понедельничного питания срок — пятница, а не понедельник.
4. Показанная сумма — расчётный остаток с учётом заказов. Создание / изменение / отмена не должны порождать фиктивное фактическое списание или возврат на карту.
5. Фактический баланс карты обновляется утром в день питания. Это процесс бэкенда; в прототипе он не выполняется.
6. Статусов заказа «Принят», «Передан на кухню» и подобных нет.
7. При нехватке средств заказ доступен после согласия «Оплачу разницу за деньги». Затем показывается сумма доплаты и окно СБП.
8. Автоматический возврат по СБП не обещаем. При отмене оплаченного заказа или уменьшении суммы показываем: для возврата оплаченных средств / переплаты нужно написать в столовую «Тимьян».
9. Контакт или URL столовой не предоставлен. Не придумывать адрес и не делать неработающую ссылку.
10. На мобильном экране итоговая панель закреплена снизу, с учётом safe area и места под ней в контенте. На широком экране панель sticky.
11. Кнопки и пункты меню имеют общее скругление 11 px. Компактная шапка: IS.Food, под ним имя и остаток, справа «Выйти».

## Где подключать методы

| Точка в `public/app.js` | Что есть сейчас | Что должен сделать разработчик |
| --- | --- | --- |
| Начальные `balance`, `current`, `past`, `history`, профиль в `profile()` / `render()` | Моковые данные | Получить пользователя, меню, заказы, расчётный остаток и историю |
| `refresh` | Таймер 450 мс | Перечитать данные, не потерять несохранённый выбор без уведомления |
| `login`, `logout-confirm` | Локальный флаг | Реальная сессия; не доверять полям формы из прототипа |
| `totals()` | Локальный предварительный расчёт | Авторитетный расчёт на сервере; суммы в минимальных денежных единицах |
| `save` | Запись в переменную `current` | Создать или обновить существующую запись, без дублирования |
| `cancel-confirm` | Удаление текущего заказа из памяти | Отменить серверную запись, пересчитать остаток; не запускать автоматический возврат денег |
| `canChangeOrder()`, `guardChange()` | Проверка часов браузера | Проверять серверное время и срок при каждом изменяющем запросе |
| `qr()`, `pay`, `bank` | Декоративный QR; имитация оплаты по кнопке | Получить платёжную ссылку / QR от сервера; подтверждать оплату только серверным событием / проверкой |
| `addHistory()` | Локальная история | Загружать реальные проведённые операции, не считать нажатие кнопки подтверждением платежа |

Не добавляйте фиктивные HTTP endpoints. Контракт API нужно согласовать с владельцем бэкенда. До подключения API режим остаётся исключительно локальным.

## Модель данных

- Заказ: `id`, `date` (дата питания), `orderDate` (день оформления / дедлайна), `items: [{selected, qty}]`, `total`, `debit`, `due`, `paid`.
- `selected` — временный индекс массива комплексов. В интеграции заменить стабильным ID комплекса.
- `debit` в текущем коде — часть заказа, учтённая в расчётном остатке, **не доказательство проведённого списания**.
- `due` — необходимая денежная доплата, `paid` — уже оплаченная сумма. Если `paid > due`, разница отображается как переплата для ручного возврата.
- Старые тестовые записи поддерживают `selected/qty` вместо `items` через `orderItems()`. Это совместимость моков, не обязательное требование к API.
- `date/orderDate` сейчас строки `ДД.ММ.ГГГГ`; API лучше возвращать ISO-даты и отдельный timestamp дедлайна.

## Обязательные доработки перед production

- Реальная авторизация, разграничение данных пользователей, серверная валидация, CSRF / защита сессии согласно стеку.
- Идемпотентность создания / изменения / отмены / оплаты. Защита от двойного нажатия и гонок.
- Состояния ошибок загрузки, сохранения, недоступного меню и изменения цены. Переход между вкладками сейчас имитирует готовые данные.
- Серверный календарь меню: сейчас дата рассчитывается из тестового дня; доступность опубликованного меню не проверяется.
- Лимит 5 порций на комплекс — параметр прототипа, не подтверждённое бизнес-ограничение. Уточнить.
- Моковые граммовки и цены блюд местами не согласованы с ценой комплекса; заменить данными источника, не выводить их из общей стоимости.
- История операций — статические примеры. Её timestamps не реализуют реальный утренний процесс обновления карты.
- Ручной возврат после обращения в столовую и его результат должен приходить с сервера; прототип его не обрабатывает. Не переносить сохранённую переплату между независимыми заказами автоматически.
- Событие `bank` нельзя оставлять как подтверждение реального платежа. Никаких реальных переводов из этого прототипа.
- CSP разрешить только конкретные API-домены после согласования интеграции, не заменять на `*`.
- Проверить доступность: клавиатурное переключение табов, восстановление фокуса модалок, экранные дикторы.

## Указание для Cursor

Сохрани визуальный интерфейс `public/` и правила выше. Сначала изучи реальные методы проекта, предложи сопоставление данных и действий. Подключай их постепенно, заменяя локальные моки, а не переписывая дизайн. Не добавляй статусы заказов, автоматические возвраты СБП или списания до проведения операции. Не используй клиентские часы или нажатие кнопки как источник истины.
